## Current state (2026-05-07)

Designer + ModelSnapshot files are now committed alongside the hand-authored migration:

- `20260506120000_Initial_AddQueueingSchema.cs` — hand-authored raw SQL Up/Down (schema, tables, partial indexes, materialised view, RLS policies, `tenant_id` COALESCE defaults)
- `20260506120000_Initial_AddQueueingSchema.Designer.cs` — `[Migration(...)]` registration + `BuildTargetModel` so EF can see the migration in the chain
- `QueueingDbContextModelSnapshot.cs` — current model state for the next `dotnet ef migrations add` to diff against

These were generated by running `dotnet ef migrations add Initial_AddQueueingSchema_RegenSnapshot` against a clean checkout, then renaming the resulting `Designer.cs` to match the original migration's timestamp/class name and discarding the throwaway no-op migration body. The hand-authored Up/Down SQL was **not** modified — EF's generated body strips the materialised view, RLS policies, partial index `WHERE` clauses, and the COALESCE-default `tenant_id`, none of which the EF fluent API can emit.

## Apply order

The queueing schema lives in the same DB (`nickerp_platform`) as `tenancy`, `identity`, `audit`. Apply order in the deploy script:

1. `tenancy` (creates the role, the COALESCE-on-tenant-id RLS pattern)
2. `audit`
3. `identity`
4. `queueing` ← added by this migration
5. Module schemas (`inspection`, `nickfinance`, etc.)

## Permissions

The `nscim_app` runtime role needs `SELECT, INSERT, UPDATE, DELETE` on `queueing.outbox` + `queueing.dead_letter`, and `USAGE, SELECT` on the IDENTITY sequences. The Sprint 5 G1-3 grants migration in `NickERP.Platform.Tenancy.Database` follows a `GRANT ON ALL TABLES IN SCHEMA` pattern that's idempotent — extend that grant to include the `queueing` schema in the next platform-grants migration.

## RLS posture

Both tables ship with `ENABLE + FORCE ROW LEVEL SECURITY` and a `tenant_isolation_*` policy using the standard `COALESCE(current_setting('app.tenant_id', true), '0')::bigint` expression. The DLQ admin UI (Sprint S+1 per plan) opts into system-context cross-tenant reads via an additional policy that ORs in `current_setting('app.tenant_id') = '-1'` — that policy is **not** in this migration; it lands when the admin UI ships.

## Adding a new migration

Now that the snapshot is in place, future schema changes are normal EF migrations:

```powershell
dotnet ef migrations add Add_QueueingFeatureName --project "C:\Shared\ERP V2\platform\NickERP.Platform.Queueing.Database"
```

EF will diff against `QueueingDbContextModelSnapshot.cs` and emit the proper `CreateTable` / `AddColumn` calls. For features that need RLS policies or materialised views, fall back to `migrationBuilder.Sql(...)` per the Tenancy `Add_RLS_Policies` convention.
